# ClimbUK on an Odoo website

The brand rules (`climb-visual-style`, `climb-voice`) say what a page looks and sounds like on any platform. This skill adds what an Odoo website needs on top, and only there: the marketing team must be able to open any page we ship, click **Edit**, and change everything the website editor can change: words, links, buttons, images, backgrounds, colour presets, and whole sections (move, copy, delete, drop new blocks between them). A page that looks right but cannot be edited is a failed delivery. Where the editor's own blocks cannot produce the look, add CSS or a small script on top of them (in the module, or the website's custom code); never replace them with markup the editor cannot handle.

## The rules

1. **Copy lives in a view.** Every word, link and image someone may want to change sits in the arch of a QWeb view: a `website.page`, or a `<template>` the controller renders with `request.render()`. Never put page copy into the page as a string: no `t-out`/`t-raw` of an HTML string, no `Markup(...)` read from a file, a field or a generator at request time, no copy written by JavaScript. The editor can only save to a view; anything else is shown but locked.
2. **Generate views, not strings.** When pages are built by a script (brand book pages, generated guidelines), the script writes the view XML (one view per page, valid XML, SVG names in their own case) at build time, and the controller renders that view. Never read generated HTML from disk in a controller.
3. **Build from the editor's own blocks.** Put the body of the page in one `<div class="oe_structure" id="oe_structure_<page>"/>` with a unique id, and make every part of it a `section` with a colour preset (`o_cc o_cc1` to `o_cc5`), a `data-name` and a `container` inside. Cards in a grid are columns of a Bootstrap `row` (each card inside its own `col-*` div). Links styled as buttons are `<a class="btn btn-primary">` (or `btn-secondary`); images are `<img class="img img-fluid">`; a photo behind a section is the section's background image (`oe_img_bg` and a `background-image` style) with an `o_we_bg_filter` div for the fade. Our own classes stay on these elements for the brand look; they never replace them.
4. **Keep live data out of the structure.** Everything inside an `oe_structure` is saved as it is shown, so a `t-out`, `t-foreach` or `t-field` inside it is frozen into the page the first time someone saves. Fetch records, counts and media-kit cards in the browser into an empty placeholder marked `o_not_editable` (with a plain link as the fallback), from an interaction that empties it again in `destroy()`. Live data outside the structure (the bar, the header of the site) can use `t-out` as usual.
5. **Scripts are interactions that undo themselves.** Anything a script changes as people use the page (search panels, theme or size switches, filters, contrast checkers, sliders, copy buttons, menus that open) runs from an interaction (`@web/public/interaction`, registered in `public.interactions`) whose `destroy()` puts back every class, attribute, text and listener it changed. The editor stops interactions before it edits and saves, so the saved page never holds a script's state. Register an edit-mode variant (`public.interactions.edit`) only for what must show while editing, such as fetched cards. Mark the tool itself `o_not_editable` so it moves with its section but its insides cannot be edited; parts outside the structure that must never be saved carry `t-ignore="true"`.
6. **Use the theme, never hard-coded values.** In an Odoo module, colours, fonts and spacing come from the website theme: colour presets (`o_cc1` to `o_cc5`), the theme's CSS variables (`--o-color-1` to `--o-color-5`, `--o-cc1-bg`, `--o-cc1-text`, `--o-cc1-headings`, `--o-cc1-link`, `--o-cc1-btn-primary` and the same for presets 2 to 5, Bootstrap variables) and its fonts, which are set to the brand tokens. Never type a hex value, font name or pixel colour in a module's templates or styles; where a page ships the token stylesheet (`tokens.css`), the brand tokens are the fallback (`var(--o-cc3-bg, var(--climb-preset-o-cc3-background))`). The website's preset rules colour headings and links inside a section, so restate your own heading and link colours with enough weight to win, from the same variables.
7. **Same on Odoo 19 and Odoo 20.** Build and test on both until the move to Odoo 20 is done. Only the manifest version and the access file may differ; features, markup and accessibility fixes are the same.
8. **Edits on the website are copies.** When someone saves a page in the editor, Odoo keeps a website-specific copy of that view (or of its structure). A later module update changes the original, not the copy. Say so in the module README, and make lasting changes in the source (the brand pack or the module) as well as on the page.
9. **Copy stays translatable and on brand.** Text in views goes through the website translator, so keep copy in the arch, not in JavaScript or CSS `content:`. Run the `climb-voice` checker on it like any other public copy.
10. **Record what you learn in the brand pack.** A brand preference or decision a person gives you while you build a page goes into the brand pack in the same piece of work: Odoo-only rules in this skill, everything else in `climb-voice` or `climb-visual-style` (see "The pack learns as it goes" in the brand pack's AGENTS.md). This copy of the skill is synced from the pack, so change it there.

## How to check a page before you call it done

On a local Odoo 19 and Odoo 20 with the module installed or upgraded:

1. As a logged-out visitor, the page answers 200, looks right in every theme the page offers, and its live data and tools work.
2. As a website designer, view the page source: the `oe_structure` carries `data-oe-model="ir.ui.view"`, a `data-oe-id` and a `data-oe-xpath`; every section has a colour preset; nothing a script fills or changes is inside the view as rendered data.
3. Click **Edit** and try each kind of change: type in a paragraph, change a button's style and link, replace an image, change a section's colour preset and background, move a section, copy a card, drop a new block between two sections. Save, and reload as a visitor: every change shows, and the live tools and data still work. Check that the locked tools cannot be edited inside. Then delete the website copy of the view (developer mode, **Settings > Technical > Views**, the copy with a website set) to put the page back.
4. Cover it with a test: an `HttpCase` that fetches the page as an admin and asserts the branded structure, the presets, the button and image classes and the locked tools, and one that saves through `ir.ui.view.save()` at the structure's `data-oe-xpath` and finds the change on the page.

Say in your final message which pages you checked, on which versions, and what you found.
